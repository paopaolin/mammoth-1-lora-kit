# 27B 决策模型微调：实验设置

> 目标模型：`baselabs/mammoth-1`（27B，MIT 许可，非 gated）
> 基线成绩：JevBench public-231 上 **217/231 = 93.94%**，Brier 0.0828，ECE 0.0194，p50 延迟 0.256s
> 目标：**不牺牲已有准确率的前提下，让置信度更可信**；准确率若能顺带涨 1–3 条算加分

---

## 1 为什么这么设：先看 27B 到底错在哪

我们的 231 条逐题结果按任务族拆开，27B 的 14 条错误分布是：

| 任务族 | 题数 | 9B 错 | 27B 错 | 说明 |
|---|---:|---:|---:|---|
| **temporal_numeric** | 15 | 8 | **7** | 时间/数值推算，占 27B 全部错误的一半 |
| **long_policy** | 19 | 5 | **3** | 长规则+例外，需要跨段落拼条件 |
| multi_hop | 18 | 5 | 2 | 参数一涨就好，9B→27B 已 +3 |
| ambiguous | 7 | 0 | 1 | 唯一一个比 9B 更差的族 |
| judge_hard | 17 | 4 | 1 | 同上，参数一涨就好 |
| 其余 13 个族 | — | 1 | 0 | 全对（tool_selection、routing、intent、extraction 等均满分） |

这张表直接决定了两件事：

**数据只投两类。** temporal_numeric（7 条）+ long_policy（3 条）占了错误的 71%。
其余族 27B 已经全对，往里投数据的唯一作用是防止遗忘。

**不要复用 9B 那份 1,166 条。** 那份是按 9B 的弱项配的，其中 98.6% 的训练量投在
tool_selection 和 routing 上——而 27B 这两族是 24 题全对。拿它训 27B 大概率是
"在满分题上过拟合、挤占原有能力"，这是我们在 9B 上实测见过的结果。

## 2 三个硬约束（会直接改变方案）

### 约束一：LoRA 只能单卡；全量必须配 FSDP

`OneJev/train/sft.py:557`（commit `81ce62f`）：

```python
if args.fsdp and not args.full_finetune:
    raise SystemExit("--fsdp shards a full fine-tune; add --full-finetune")
```

两条路互斥，但**两条都通**，只是资源形状不同：

| 路线 | 单 run 用卡 | 显存/卡 | 32 卡能同时跑几个 | 适配本任务？ |
|---|---|---|---|---|
| LoRA（r32, α64, q/k/v/o） | 1 | 推算 60–65GB | **8–12 个** | ✅ 数据 1,250 条，容量小反而不容易过拟合 |
| 全量 + FSDP | 8 | 约 54GB（fp32 主权重） | **4 个**（3 个更稳，给评测留卡） | ⚠️ 能跑，但 1,250 条全量微调容易把校准弄坏，只当对照臂 |

全量不是我们编的路线：OneJev 官方就带 `train/configs/onejev_27b_full.yaml`
（`full_finetune: true` + `fsdp: true`, lr 5e-6, 1 epoch, batch_tokens 16384,
max_rows 64, warmup 3%, grad clip 1.0），`scripts/train_27b_full.sh` 就是照它写的。

**结论：32 张卡不是把一次训练拆开，而是「8 张单卡 LoRA + 3 个 8 卡全量」同时跑。**
见第 4 节的分配表。

### 约束二：显存没实测过，必须自己探

我们这边 8 张卡当时全被占满，**没能给你一个实测数字**。按结构推算（54.7GB 权重
+ LoRA 参数与优化器约 0.9GB + 梯度检查点后的激活约 1.5GB + CUDA 上下文碎片约 2GB）
应该在 **60–65GB**。96GB 的 H20 放得下，80G 的卡就比较紧。

但这是**推算不是实测**。所以第一步就是 `scripts/probe_memory.sh`：它跑真实训练循环
5 分钟，读 `sft.py` 自己打印的 `mem` 字段。判读标准：

| 实测 mem | 结论 |
|---|---|
| < 85G | 96G 单卡随便跑，`--batch-tokens` 可以往上加到 4096 试 |
| 85–95G | 把 `--batch-tokens` 降到 1024 |
| OOM | 降到 512；仍 OOM 就只能走全量 + FSDP |

### 约束三：H20 是 Hopper，必须装 tilelang

`flash-linear-attention` 在 **Triton 3.4.0–3.7.1 + Hopper** 上，`gated chunk_bwd_dqkwg`
这个反向 kernel **算出的梯度是错的但不报错**。H20 和 H100 都是 sm90，一样中招。

我们 9B 那轮的实际报错：

```
RuntimeError: Triton >= 3.4.0 and < 3.7.1 on Hopper GPUs produces incorrect results
for gated chunk_bwd_dqkwg. Please upgrade Triton to >= 3.7.1 or install tilelang
```

装 `tilelang==0.1.15` 后 fla 自动切后端（日志里能看到
`[FLA Backend] chunk_bwd_dqkwg -> tilelang`）。**没有这个检查的话，训练会正常跑完、
loss 也正常下降，你得到一个看起来成功但权重是坏的模型。** `scripts/check_env.py`
会替你把这一条查出来。

## 3 数据

### 组成

| 文件 | 条数 | 用途 | 来源构成 |
|---|---:|---|---|
| `train_targeted.jsonl` | 1,250 | **主臂** | DROP 500 + When2Call 300 + 长政策合成 250 + 短场景合成 200 |
| `train_anchor.jsonl` | 300 | 对照臂 | 纯 When2Call |
| `val.jsonl` | 175 | 选 checkpoint | DROP 75 + When2Call 50 + 长政策 25 + 合成 25 |
| `heldout.jsonl` | 175 | 最终报告 | 同上比例，与 val 不重叠 |

### 四个来源各自解决什么

**DROP（500 条）** —— 补 temporal_numeric。从 77,400 条里筛出 15,088 条可用：
只留答案是单一数字或日期的题，按"需要算一步"打分（出现 more/less/total/difference/
before/after 等词，或同段落有 ≥3 个同量级数字），取高分优先。
干扰项**从同一段材料里取同量级数字**，这是真实混淆源——比如问"上半场一共得了几分"，
正确答案 29，干扰项里放 26（其中一队的得分），而不是随机凑一个 50。

**长政策合成（250 条）** —— 补 long_policy（27B 错 3 条）。公开数据里没有
"一般条款 + 例外条款 + 具体情形"的同分布语料，所以只能合成。6 个规则族
（退货时效、注销删除 vs 财税留存、超限额审批、生产数据导出、加班上限、液体限额），
每题的输入由「一般条款 / 例外条款 / 具体情形」三段拼成，标签由规则引擎
按**先例外、再一般**的顺序算出。关键点有两个：一是每族都埋了"信息不足"样本
（关键字段缺失导致两个答案都说不通），防止模型退化成二选一瞎猜；二是生成时
对 `(policy, case) → answer` 做唯一性断言，同句出现两个 gold 就直接中断
（早期版本真的踩过）。**这 250 条是合成的，只能教"先看例外"这个推理顺序，
教不了真实政策文本的语言复杂度**，边际收益未知，请当可插拔的一臂单独评估。

**短场景合成（200 条）** —— 解决分布错位。DROP 的 passage 中位约 2,700 字符，
而 JevBench 的场景题只有 70 字符左右。9B 那轮就吃过这个亏：训"长材料摘数"、
评"短场景判断"，迁移有限。所以合成了 4 类短题（期限推算、时长相加、折扣计算、
边界判定），**标签全部由 Python 的 datetime / Decimal 算出来，不是人工标的**，
并且刻意把多数样本放在边界上（比如"不超过 48 小时"，恰好 48 小时该受理、
48 小时零 1 小时不该受理），考的就是"不超过"是否含等于。

**When2Call（300 条）** —— 只作锚点，不作目标。27B 在这族已经 12/12 全对，
放它是为了在训练 temporal 的同时别把工具决策的行为带偏。

### 已知问题（诚实写在这里）

1. **When2Call 有标签歧义**：同一个用户请求在偏好数据里配了两个不同的"选中回复"
   （一个调工具、一个反问）。原始 7,290 条里有 32 个请求属于这种情况，**已整组剔除**，
   实际可用 7,210 条。如果你要扩数据，这个过滤必须保留。
2. **DROP 的答案依赖抽取质量**：我们只保留单答案、且答案是数字/日期的题，
   多答案题和文本答案题全部丢弃（占比不小，但强行改造会引入标签噪声）。
3. **合成数据不是真人标的**：规则清楚、标签可程序验证，但语言多样性差。
   建议当作独立一臂看，不要和真实数据混着下结论。
4. **long_policy 那 250 条是合成的**，见上面第四节。第一轮建议加一臂
   `tgt_no_longpolicy`（925 条）做消融，看这 250 条到底是帮忙还是纯噪声。

### 1,250 条够不够

分三个问题看，答案不一样：

| 问的是什么 | 够不够 | 依据 |
|---|---|---|
| 够不够撬动那 14 条错题 | **够**，但只够撬 1–3 条 | 9B 那轮 1,166 条撬动了 2 条（208→210）；数据是照错题族配的，不是随机抽的 |
| 够不够让 27B 学到新能力 | **远远不够** | mammoth-1 自己是 6.21M 条、9,859 步训出来的；我们 0.75M token 连零头都不到 |
| 够不够做可信的 A/B | **不够**，得靠 seed | 231 条评测集一条 0.43%，±2 条的差异可能纯粹是种子噪声 |

换算成实际训练量（按 tokenizer 估，中位 602 token/条）：

| 数据 | token | LoRA 2ep（bt2048） | 全量 1ep（bt16384） |
|---|---:|---:|---:|
| 1,250 条 | 0.75M | **735 步** | **46 步** |
| 1,750 条（DROP 扩到 1,000） | 1.16M | 1,134 步 | 71 步 |

**46 步这个数要留意。**全量微调在 1,250 条上只走 46 个优化步，3% 的 warmup 等于
1 步、cosine 在 46 步里衰减完——它更像"轻轻推一下"，而不是一次微调。
好处是不容易把模型推坏，坏处是**不同 seed 之间差异会很大**，单 seed 比 LoRA 与全量
基本没有意义。这也解释了为什么第二轮必须 3 个 seed。

结构上限（不是钱的问题，是数据本身的天花板）：

- `long_policy` 六个规则族的去重空间加起来约 **620 条**，再多会静默少给。
  要突破得给它加新的变量轴（比如再拆一个"时限是否已过"的维度），不是调大数字就行。
- `DROP` 筛完还有 **14,588 条**没用，扩到 1,000 / 2,000 都是现成的，代价只是训练时间。

**怎么判断该不该加数据**，看两个信号：

1. train loss 已经很低、val 和 231 都不动 → 加数据没用，问题在"数据不对症"
   （模型没在错题上学到可迁移的东西），该换构造方式而不是加量。
2. val 随着数据量还在降 → 欠拟合，继续加。这时候用现成的 1,750 条版本测一臂：

```bash
python scripts/make_scaled.py --drop 1000     # -> data/train_targeted_2x.jsonl（1,750 条）
```

它只放大训练集，val/heldout 逐条沿用原文件——否则"涨了"分不清是数据量还是换了题。
第一轮如果看到欠拟合迹象，第二轮直接加这一臂（其余超参与主臂完全相同）。

## 4 32 张 H20 怎么排

两种 run 混着排，因为它们的资源形状不一样：**LoRA 吃 1 张卡，全量吃 8 张卡。**
一个 27B LoRA run（1,250 条 × 2 epoch）预计 **1.5–3 小时**（H20 算力弱于 H100，
但显存带宽 4.0TB/s 高于 H100 的 3.35TB/s，小 batch 训练是带宽瓶颈，所以差距
没有纸面 FLOPs 那么大）；一个全量 run 计算量更小（1 epoch、64 rows/step，
约 20 步就结束），但 FSDP 初始化 + 54.7GB 权重加载 + 优化器状态构建要 1 小时上下，
合计 **2–3 小时**。

### 第一轮：32 张卡满配（8 个 LoRA + 3 个全量）

| 卡 | 实验名 | 路线 | 数据 | 关键参数 |
|---|---|---|---|---|
| 0 | `base_eval` → `tgt_2ep_lr1e5` | 先评测再训练 | — / targeted | 先复现 93.94%，再跑主臂 |
| 1 | `tgt_2ep_lr5e6` | LoRA | targeted | 2ep, lr 5e-6 |
| 2 | `tgt_2ep_lr2e5` | LoRA | targeted | 2ep, lr 2e-5 |
| 3 | `tgt_1ep_lr1e5` | LoRA | targeted | 1ep |
| 4 | `tgt_2ep_lr1e5_brier3` | LoRA | targeted | brier_weight 3.0 |
| 5 | `tgt_2ep_lr1e5_brier5` | LoRA | targeted | brier_weight 5.0 |
| 6 | `tgt_no_longpolicy` | LoRA | 1,000（去掉长政策） | 2ep, lr 1e-5 |
| 7 | `anchor_2ep_lr1e5` | LoRA | anchor 300 | 对照臂 |
| 8–15 | `full_1ep_lr2p7e6` | **全量 FSDP** | targeted | lr 2.7e-6（mammoth-1 原始峰值） |
| 16–23 | `full_1ep_lr1e6` | **全量 FSDP** | targeted | 半强度 lr |
| 24–31 | `full_2ep_lr5e6` | **全量 FSDP** | targeted | lr 5e-6 × 2ep，故意过量 |

启动方式：LoRA 那 8 张用 `run_round1.sh`（`GPUS=0,1,...,7`），全量三个各起一条

```bash
bash scripts/train_27b_full.sh 8,9,10,11,12,13,14,15  data/train_targeted.jsonl full_1ep_lr2p7e6
bash scripts/train_27b_full.sh 16,17,18,19,20,21,22,23 data/train_targeted.jsonl full_1ep_lr1e6   LR=1e-6
bash scripts/train_27b_full.sh 24,25,26,27,28,29,30,31 data/train_targeted.jsonl full_2ep_lr5e6   LR=5e-6 EPOCHS=2
```

**为什么全量默认 lr 是 2.7e-6，而 OneJev 配置里写的是 5e-6？** 这是两件事。
`onejev_27b_full.yaml` 是拿 Qwen3.8-27B **从头做决策后训练**的配方；
mammoth-1 的模型卡写得很清楚：它自己是 6.21M 条、1 epoch、**peak LR 2.7e-6**、
AdamW β 0.9/0.95、无 weight decay、3% warmup、cosine、Brier λ=1、视觉塔冻结。
我们现在是**接着一个已经收敛的模型往下训**，峰值抬到 5e-6 没有道理。
所以 2.7e-6 是主臂，5e-6 只当"压力档"放第三个臂，预期它会把 ECE 弄坏。

三个臂的意图：2.7e-6 是"照原配方接着训"；1e-6 是"半强度，看能不能只动一点点"；
5e-6×2ep 是"故意过量"。**如果过量那档 ECE 没变差，说明"全量伤校准"这个判断
在我们这份数据上不成立**——那反而是个有价值的结论。

**卡 0 的基线复现必须先看**：复现不出 93.94%，说明环境或推理口径有问题，
后面所有对比都不成立。这一步同时也是注意力配置的判据（见 `docs/03` 第 3 节）。

**磁盘要先看**：每个全量 run 的 `final/` 约 55GB，三个就是 165GB。别在快满的
盘上起，写到一半失败比不跑更浪费时间。

`tgt_no_longpolicy` 不是顺手加的：1,250 条里有 450 条是合成数据，占 36%。
**如果 250 条长政策对 long_policy 那族没帮助、甚至拖累整体，就该把它摘掉。**
判断方法：与卡 0 的 `tgt_2ep_lr1e5` 比，231 上不降且 heldout ECE 更好，
就说明合成政策是负资产。

### 第二轮：确认与稳定性（第一轮胜出的配置 × 3 个 seed）

第一轮胜出的配置重跑 3 个随机种子（`--seed 0/1/2`），确认提升不是噪声。
231 道题的粒度是 0.43%，涨落 1–2 条完全可能在 seed 噪声范围内——
**只看单 seed 就下结论是这个规模评测集上最常见的错误。**

如果全量赢了，它一个 seed 要 8 张卡：3 个 seed 就是 24 张，剩下 8 张跑软标签：

| 卡 | 实验 | 说明 |
|---|---|---|
| 0–23 | 全量胜出配置 × seed 0/1/2 | 每个 seed 8 卡 |
| 24–31 | `tgt_soft_2ep_lr1e5` 等 | 软标签 LoRA 对照，见 `scripts/make_soft_labels.py` |

如果 LoRA 赢了，第二轮就是纯单卡：12 张跑 seed，剩下 20 张跑消融
（`tgt_no_anchor` / `tgt_drop_only` / `tgt_short_only` / 软标签两档，
 外加一臂 `tgt_2x` 用 `data/train_targeted_2x.jsonl` 的 1,750 条，
 看数据量是不是瓶颈，见第 3 节末尾的判据）。

软标签注意：teacher 分布必须先用**原始**模型在训练集上跑一遍得到，
不能用已经微调过的模型自己蒸馏自己。

### 第三轮：评测（32 张卡全用上）

一个模型在三个集合上评测约 20 分钟（public-231 约 3 分钟，两个 1,200 条各 5–8 分钟）。
第二轮产出的 12 个最佳 adapter + 卡 0 的基线，并行一轮就能全部评完。

## 5 评测协议（这部分别省）

每个模型都要在**三个集合**上评，缺一不可：

| 集合 | 条数 | 看什么 |
|---|---:|---|
| JevBench public-231 | 231 | 主成绩，和基线 93.94% 直接对比 |
| `eval_sets/crossbench_random_1200.jsonl` | 1,200 | 通用能力有没有退化（随机负样本，偏简单） |
| `eval_sets/crossbench_hard_1200.jsonl` | 1,200 | **置信度在难样本上还准不准**（难负样本） |

public-231 不在这个包里（版权在 jevbench），自己拼：

```bash
cat jevbench/datasets/public/{easy,original,hard}.jsonl > eval_sets/public_231.jsonl
```

### 必须报的指标

不要只报准确率。按这个顺序看：

1. **准确率**（对题数 / 231）
2. **ECE**：和基线的 0.0194 比。**27B 本来校准就很好，任何 LoRA 大概率会把它弄差**
3. **0.9 阈值下的采纳精度与覆盖率**：这是路由能不能用的直接判断
4. **难负集上「高置信却答错」的条数**。基线数字要**你在新版难负集上先测一遍再定**——
   我们旧版这套题有构造缺陷（详见 docs/04 第 5 节），基线 12 条 / 98.11% 已作废，不要拿它当目标。
   但 **public-231 上的路由基线是实测的、没有受那个 bug 影响**（bug 出在我们自己合成的
   难负样本上，不出在 jevbench 官方集），可以直接拿来做标准，见下表。
5. **温度 T**：在 `val.jsonl` 上拟合，不要用 231 拟合（我们 9B 那轮用了测试集，
   这是已知缺陷，这轮改掉）

用 `scripts/collect_summaries.py` 一次性出表（accuracy/brier/ece 读 `summary.json`，
覆盖率/采纳精度/高置信错误数从 `results.jsonl` 的 probs 现算）：

```bash
python scripts/collect_summaries.py 'results/*/summary.json' --thresholds 0.8,0.9,0.95
```

### 我们的实测基线（public-231，非合成集，可信）

| 模型 | acc | corr/231 | brier | ECE | cov@0.9 | prec@0.9 | 高置信错误 |
|---|---:|---:|---:|---:|---:|---:|---:|
| **mammoth-1 27B 基线** | 93.94% | 217 | 0.0828 | 0.0194 | **0.797** | **1.000** | **1** |
| elephant-1 9B 基线 | 90.04% | 208 | 0.1289 | 0.0338 | 0.727 | 0.994 | 2 |
| 9B + R3 软标签 + 温度校准 | 90.91% | 210 | 0.1346 | 0.0502 | 0.758 | 0.994 | 3 |

第一行就是你要守的那条线：**27B 在 0.9 阈值下采纳 184 条（79.7%），一条都没错。**
它的置信度现在是能用的，任务是不把它弄坏。作为对照，9B 那轮最差的一档（R1）
在这列是 cov 0.939 / prec 0.935 / 高置信错误 18 条——**覆盖率涨了 14 个百分点、
代价是把 17 条新错误包进了高置信区**。这就是"以校准换准确率"长什么样。

### 成功标准

**不看"有没有涨点"，看这四条同时成立**：

- 231 准确率 ≥ 217（不下降）
- heldout 上的 ECE 不比基线差太多（比如 ≤ +0.01，基线 0.0194）
- 0.9 阈值下采纳精度 ≥ 0.99，且覆盖率 ≥ 0.75（基线 1.000 / 0.797）
  精度 1.000 是 231 条上的巧合还是真实水平，要靠多 seed 和难负集交叉验证；所以这里留了
  0.99 的余量，但**不允许用大幅牺牲覆盖率的方式刷精度**——两条必须同时满足
- 难负集高置信错误数不高于你自己测出的基线（旧版的 12 条已作废）

只要有一条明显破了，这轮就应记为"以校准换准确率"的负面结果——
这在 9B 上真实发生过（R1：准确率 +1 条，ECE 从 0.0338 恶化到 0.0840，
高置信错误从 1 条涨到 14 条）。

## 6 这轮不做什么（避免白跑）

**不把 long_policy 当主战场。** 27B 在这族错 3 条，公开数据集里没有同分布语料，
所以我们用 250 条规则引擎合成数据做**可插拔的一臂**（卡 6 的 `tgt_no_longpolicy`
就是它的对照）。这一臂赢了才留，没赢就摘掉——不要把它的存在当成既定结论。

**不把全量微调当默认路线。** 它有 8 卡 FSDP 的官方配方，能跑，也确实在矩阵里
（卡 8–31）。但 1,250 条样本全量微调 27B，梯度覆盖整个参数空间，
最容易出的事就是"准确率不降、置信度全乱"——而置信度恰好是这轮唯一在意的东西。
所以它是**对照臂**，不是主臂；除非它在四条成功标准上同时赢过 LoRA，否则不采纳。

**不用 231 条调任何超参。** 231 只用于最终报告。选 checkpoint 用 `val.jsonl`，
拟合温度也用 `val.jsonl`。这轮刻意修正了 9B 那轮的测试集调参问题。

**不追 SOTA 分数。** 27B 距离满分还有 14 条，其中 7 条是结构性难题
（9B 微调 8 条、27B 微调 8 条、13 倍参数也只多 5 条）。这轮的价值在于
把"微调之后置信度还能不能信"这件事测清楚，给后续决策留依据。

## 7 我们需要回传什么

每个 run 四样，缺一样结论就没法复核：

```
runs/<run_name>/
├── adapter/                     LoRA 的 adapter 权重（约 200MB，全量 run 里叫 final/）
├── merged/                      训练时加 --merge 才有：合好的完整模型，直接拿去评
├── summary.json                 jevbench summarize 的输出（三个集合各一份）
├── results.jsonl                逐题结果（含 probs），这是能复算 ECE/路由的原始数据
└── train.log                    训练日志（含每步 loss / mem / 是否有 FLA Backend 切换）
```

回传时，LoRA run 给 `summary.json` + `results.jsonl` + `train.log` + `adapter/`
（`merged/` 和 `final/` 有 55GB，别传，回来我们自己合）。
全量 run 没有 adapter，就只回前三样；**如果最后是全量那臂赢了，再把它的
`final/` 传到网盘或 HF 上**，一个 55GB 就够，不用每个 seed 都传。

如果空间紧张，`results.jsonl` 和 `summary.json` 必须留，adapter 可以只留最终入选的几个。
